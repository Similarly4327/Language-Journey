# Language Passport CSV v1

`passport-csv.js` is a pure transform. It never reads storage, changes mastery, unlocks lessons, fetches audio, or executes instructions. The browser loads Papa Parse 5.5.3 before the Passport module. Node uses `require('../passport-csv.js')`. [MIT license](../assets/vendor/papaparse.LICENSE.txt) · [Example Passport](language-passport-v1.example.csv)

Canonical output is UTF-8 with BOM, comma separated, CRLF terminated, and every field quoted. Each record has exactly these 24 columns, including empty values:

```text
record_type,schema_version,language,key,value,lexeme_id,sense_id,course_id,word,reading,romaji,word_type,meaning,context_category,example_sentence,example_translation,dictionary_explanation,learning_note,source,course_level,course_lesson,knowledge_status,audio_ref,acquired_at
```

`schema_version` is `1`; ISO language code is `ja`. UI/file label `JP` may be used by the app, but is not the CSV language value. PROFILE rows precede INSTRUCTION rows, followed by knowledge rows. Profile keys are caller supplied actual selector values; structured values (including current JLPT selectors and guideline version) are JSON serialized in `value`. Missing profile statistics are omitted, never defaulted to invented values. The module does not calculate proficiency.

Record types: PROFILE (key/value), INSTRUCTION (key/value plain text), VOCABULARY, SENSE, CONTEXT, GRAMMAR, PARTICLE, SCRIPT and KANJI. A context references its lexeme/sense and carries an example, translation and optional category. It does not increase the unique word count. `word` is the written lemma; `reading` the pronunciation; `meaning` the particular sense. All other fields are optional explanatory/source data. Export callers select actual introduced/Recall-eligible knowledge and may include actual registry references/status; this module does not infer eligibility. The supplied start prompt is `START_PROMPT` and appears by default. No personal names or statistics are synthesized.

## Formula protection and round trip

Before CSV quoting, fields whose first non-whitespace character is `=`, `+`, `-`, `@`, a tab, CR, LF or apostrophe receive one leading apostrophe. Original apostrophes are therefore doubled. Import removes exactly one leading apostrophe only when the remaining string starts with a protected sequence. This makes formula-looking values inert in spreadsheet opening while preserving values on a Passport round trip, including literal apostrophes. Third-party generators must follow this escaping convention; a leading apostrophe before a protected value denotes the escape. Spreadsheet editors that strip or reinterpret text cannot guarantee a lossless round trip; import never guesses at their conversions.

PapaParse performs CSV parsing without dynamic typing or evaluation. Comma and semicolon are accepted only when exactly one parses into the exact fixed header. No delimiter guessing based on data rows, no `sep=` preamble, no arbitrary header aliases. A BOM is accepted. Quoted commas, quotes, CRLF and Japanese Unicode survive parsing. Limits are 5 MiB UTF-8, 20,000 data records and 16,000 UTF-16 code units per field. Invalid controls, isolated surrogate halves, unsupported versions/languages/types, bad widths and parser errors produce row errors. `row` denotes the CSV record number (header = 1), including records containing quoted newlines.

## API and trust boundary

`exportCSV({profile, instructions, items})` returns text. Items accept `id`, `kind`, `lemma`/`jp`, `reading`/`kana`, `meaning`, `senseId`, `officialId`, `romaji`, `explanation`, `note`, `source`, `status`, and `contexts`. Canonical CSV field names are accepted too. Contexts accept canonical snake_case fields or `exampleSentence`, `exampleTranslation`, `category`. Structured contexts become separate rows. Export source/status is supplied by trusted app selectors.

`parseCSV(text)` returns `{valid, rows, errors, warnings, delimiter}`. `planImport(textOrParsed, {registry, personalItems})` returns `{valid, rows, counts, errors, warnings}`. No mutations occur. Registry may be an array or ID-keyed object; pass the full available registry, including locked/future/optional route entries. Entries support existing `jp`, `kana`, `meanings`, `kind:'woord'` and normalized item shapes. Registry `aliases` must be vetted written-form aliases. NFC normalization preserves distinct homophones; readings are never discarded and no stemming/conjugation guessing occurs.

Plan item: `{kind, lemma, reading, romaji, meaning, sense, senseId, wordType, explanation, note, source, contexts, officialId?}`. Import source is always `Passport Import`; untrusted claims about mastery, IDs, course references, audio, profile statistics and dates are never copied into the plan item. Official references are obtained only from a matching passed registry entry. Reliable exact IDs additionally require matching kind, lemma/alias, reading and meaning. Otherwise lexical/sense matching is used. Same spelling and reading with a new meaning produces `new-sense`, preserving official linkage while requiring review. Multiple possible homophone/sense matches produce `ambiguous` candidates for manual review, never an automatic merge. No match produces `personal`, leaving ID allocation to app storage. Non-vocabulary knowledge remains distinct by kind.

Row statuses: `official`, `personal`, `new-sense`, `duplicate`, `ambiguous`, `error`. Rows carry `item`, `officialId`, registry-only `officialRefs`, `candidates`, `errors`, and optionally `existingId` or `duplicateOf` (record number). Repeated senses and repeated existing personal overlays are duplicates. Duplicate/context rows retain context/note text for explicit additive review; the app may merge approved missing context into the original identity without touching SRS. `ambiguous` and `new-sense` require review. Global or row validation failures must prevent committing the entire invalid file. PROFILE and INSTRUCTION are ignored during planning. They are never executed or treated as evidence of mastery. Existing IDs/history remain owned by app storage, not CSV values.

## Future contribution contract (not implemented)

A future, separately selected download may contain only `language,lemma,reading,word_type,meaning,neutral_definition,audio_status`. Every field is reviewed and selected by the user before explicit sharing. Exclude personal IDs, profile, account identifiers, level, mastery/SRS, dialogue history, personal examples, notes and private sources. No automatic upload, client-side GitHub writing, credentials, new backend, or contribution UI is included in this MVP. Developer review must verify deduplication, pronunciation, licenses and publication permission before assigning central identity. Reuse the existing audio backlog/batch/manifest process and actual subscription capacity; no fixed inferred budget. Later official/audio matches must preserve local personal identity and review history through the same verified lexical matching boundary.
